# Command: sync-spec

> 진행 중이거나 수정된 사항을 Tech Spec에 반영하고 변경 내용을 보고하는 절차서입니다.
> 요건 변경, 구현 중 발견된 차이, 디자인 수정 등 모든 변경을 Spec과 동기화합니다.

---

## 언제 실행하는가

- 구현 도중 Spec과 실제 코드가 달라진 것을 발견했을 때
- 사용자가 요건을 변경했을 때 ("~를 바꿔줘", "~는 빼줘")
- 디자인이나 UI 구성이 바뀌었을 때
- `implement-poc` Step 6 완료 후 Spec 불일치가 있을 때
- 리뷰 수정 후 Spec에 반영이 필요할 때

---

## Step 1 — 현재 Spec 상태 파악

`docs/tech-specs/{feature-name}.spec.md`를 읽고 현재 상태를 확인합니다.

```
현재 Spec 상태:
- 파일: docs/tech-specs/{feature-name}.spec.md
- 상태: {draft / approved / deprecated}
- 마지막 수정: {날짜}
- Goals: {현재 Goals 목록}
```

- [ ] Spec 파일이 존재하는가?
- [ ] 현재 상태(status)를 확인했는가?

---

## Step 2 — 변경사항 수집

코드, 사용자 요청, 리뷰 결과를 바탕으로 변경된 내용을 수집합니다.

아래 세 가지 영역을 각각 확인합니다.

### 기능 및 구현 변경

```
확인 항목:
- Goals에 추가/제거된 기능이 있는가?
- Non-Goals로 이동한 항목이 있는가?
- API 엔드포인트나 응답 구조가 바뀌었는가?
- 컴포넌트 구조나 데이터 흐름이 바뀌었는가?
```

### 디자인 변경

```
확인 항목:
- Component Tree가 바뀌었는가?
- UI 상태 관리 방식이 바뀌었는가?
- 추가/제거된 컴포넌트가 있는가?
```

### 그 외

```
확인 항목:
- Edge Cases에 새로 발견된 예외 상황이 있는가?
- Testing 시나리오가 바뀌었는가?
- Open Questions에 추가할 미결 사항이 있는가?
```

---

## Step 3 — Spec 업데이트

변경사항을 Spec에 반영합니다.

### 업데이트 규칙

- 상태를 `approved` → `draft`로 변경합니다
- 변경된 섹션만 수정합니다 (변경 없는 섹션은 건드리지 않습니다)
- 섹션 10 (Open Questions)에 미결 사항을 추가합니다
- 변경 이력 주석을 섹션 상단에 추가합니다

```md
<!-- {YYYY-MM-DD} 변경: {한 줄 요약} -->
```

- [ ] 변경된 섹션이 업데이트되었는가?
- [ ] 상태가 `draft`로 변경되었는가?

---

## Step 4 — 변경 보고

업데이트 완료 후 아래 형식으로 보고합니다.

> 🟢 채비: Tech Spec을 업데이트했습니다.
>
>         현재 Spec 상태:
>         - 파일: `docs/tech-specs/{feature-name}.spec.md`
>         - 상태: draft (재검토 필요)
>
>         변경된 기능 및 구현 내용:
>         - {변경 항목}: {이전} → {이후}
>         - {추가된 항목}
>         - {제거된 항목} (Non-Goals로 이동)
>
>         변경된 디자인:
>         - {Component Tree 변경 내용}
>         - {UI 상태 변경 내용}
>         - 없음 (변경 없는 경우)
>
>         그 외:
>         - {새로 발견된 Edge Case}
>         - {미결 사항 (Open Questions 추가됨)}
>         - 없음 (변경 없는 경우)
>
>         변경된 Spec을 확인해주세요.
>         승인하시면 다음 작업을 계속하겠습니다.

- [ ] 사용자가 변경된 Spec을 확인했는가?
- [ ] 승인 후 상태를 `draft` → `approved`로 변경했는가?

---

## Step 5 — 후속 처리

Spec 승인 후 영향받는 테스트와 코드를 수정합니다.

| 변경 유형 | 후속 처리 |
|-----------|-----------|
| Goals 변경 | 영향받는 테스트 수정 → `implement-poc` 해당 Step 재실행 |
| 디자인 변경 | 컴포넌트 수정 → 테스트 재실행 |
| API 변경 | Query/Mutation 훅 수정 → 테스트 재실행 |
| Edge Case 추가 | 테스트 케이스 추가 → 테스트 재실행 |
| Non-Goals 이동 | 관련 코드 제거 또는 주석 처리 |

- [ ] 영향받는 테스트를 수정했는가?
- [ ] `pnpm exec vitest run`이 통과했는가?

---

## Spec과 코드는 항상 함께 커밋합니다

> Spec만 변경하거나 코드만 변경하는 커밋은 나중에 불일치를 만듭니다.
> sync-spec 실행 후 변경사항은 같은 커밋 또는 PR에 포함하세요.
